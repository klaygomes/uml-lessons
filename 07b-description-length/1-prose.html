Two tests, priced like a septillion lists

The help desk wants your filter. Its inbox gets one kind of junk, phishing, and the team has just added the newest feature to the catalogue: feature 20, P, the message asks for a password. Features 7 to 19 were added for the main inbox, for things like newsletters and calendar invites, and they never show up in the help desk’s mail. On the help desk’s mail, junk is easy to describe:

if it asks for a password:     junk
else if the sender is unknown: junk
otherwise:                     keep

Two tests. You know the drill from lesson 7a. The reviewer wants a certificate of at most 0.20 at confidence δ=0.05\delta = 0.05δ=0.05, with the weights written into the change before any labels are drawn, and the help desk can afford 1,500 labels. You run SRM, the structural risk minimization of lesson 7a, which ships the list whose empirical risk plus its own gap is smallest, with the weights the reviewer already signed, w(n)=6/(π2n2)w(n) = 6/(\pi^2 n^2)w(n)=6/(π2n2), and SRM does its job: the list it ships labels every message exactly as the one above. Then the certificate comes back. 0.2381. Rejected.

Read it top to bottom. A list’s size is the larger of its number of tests and its highest feature number, so sizes 1 to 19 cannot test feature 20. Without the password test, the best a list can do is a true risk, the chance of mislabelling the next message, of 0.3: “unknown sender, junk; otherwise keep”, for example, misses the quarter of messages that ask for a password from a known sender. On the labels, the best of them is wrong on more than a quarter. At size 20 the fit is excellent, 0.088, just under the 10% of labels that users flip. The fit is not the problem. The gap is.

Recall from lesson 7a the gap that SRM gives every list of size nnn, for a finite class Hn\mathcal H_nHn​ and a weight function www:

That is the bug. SRM charges a list for the company it keeps. The help desk list says very little, two tests, but it shares its size with 8.4 septillion other lists, almost all of them long monsters, and its certificate is priced as if it could be any of them. What we want is a certificate that charges a list for what it actually says. By the end of this lesson you will have one, you will see why it is a precise version of Occam’s razor, and you will see the catch hidden in the razor.

Lists by the bit: minimum description length

SRM spreads the budget over classes, and that is the help desk’s whole problem. There is a sharper version: spread it over individual hypotheses. Our H\mathcal HH is countable (each list is a finite object), so we can list its members as h1,h2,…h_1, h_2, \dotsh1​,h2​,… and write it as a union of one-member classes, H=⋃n{hn}\mathcal H = \bigcup_n \{h_n\}H=⋃n​{hn​}. Then each hypothesis gets its own weight w(h)w(h)w(h), say 1/128 for the list “unknown sender, junk; otherwise keep”.

A single fixed hypothesis has uniform convergence with no union bound at all. Now the prior knowledge is entirely in the weights. Where do good weights come from? From writing hypotheses down.

Description languages. Fix the alphabet Σ={0,1}\Sigma = \{0, 1\}Σ={0,1} (the capital Greek sigma names the set of symbols we may write). A string is a finite sequence of symbols, such as σ=(0,1,1,1,0)\sigma = (0, 1, 1, 1, 0)σ=(0,1,1,1,0), of length ∣σ∣=5|\sigma| = 5∣σ∣=5: around a string, the bars mean its length, a third meaning after “how many” and “absolute value”. The set of all strings, of every finite length, is Σ∗\Sigma^*Σ∗, the star meaning “any number of symbols”. A description language for H\mathcal HH is a function d:H→Σ∗d: \mathcal H \to \Sigma^*d:H→Σ∗ that maps each hypothesis hhh to a string d(h)d(h)d(h), its description. Its length is written ∣h∣|h|∣h∣, the description length of hhh. The language is prefix-free if for every two distinct h,h′h, h'h,h′, d(h)d(h)d(h) is not a prefix of d(h′)d(h')d(h′): no description is exactly the first ∣h∣|h|∣h∣ symbols of a longer one.

Here is a prefix-free language for decision lists. First, a code for feature numbers: write jjj in binary, with bbb digits, and put b−1b - 1b−1 zeros in front. So 1 is 1, 2 is 010, 3 is 011, 4 is 00100, 5 is 00101, and feature jjj costs 2⌊log⁡2j⌋+12\lfloor \log_2 j \rfloor + 12⌊log2​j⌋+1 bits. Read that inside out: log⁡2j\log_2 jlog2​j is the power of 2 that gives jjj, the brackets ⌊⋅⌋\lfloor \cdot \rfloor⌊⋅⌋ round it down to a whole number, and that whole number plus 1 is how many binary digits jjj has; doubling it and adding 1 counts the digits plus the leading zeros. In plain words: a feature number costs twice its binary digit count, minus one. For j=5j = 5j=5, log⁡25=2.32\log_2 5 = 2.32log2​5=2.32, rounded down to 2, so 2×2+1=52 \times 2 + 1 = 52×2+1=5 bits, and indeed 00101 has five. A reader can always tell where a feature number ends: count the leading zeros, then read one more digit than that. Then a list is written test by test: a 1 meaning “a test follows”, the feature’s code, and the test’s label bit; and at the end a 0 meaning “no more tests”, followed by the default label bit.

The list “unknown sender, junk; otherwise keep”, ((3,1);0)((3, 1); 0)((3,1);0), is written 1 011 1 0 0, which is 7 bits. “Everything is junk”, (();1)(();1)(();1), is 01, which is 2 bits. The three-test list from lesson 7a’s opening, ((3,1),(1,0),(2,1);0)((3, 1), (1, 0), (2, 1); 0)((3,1),(1,0),(2,1);0), takes 15 bits, the five-test list fff takes 29, and the help desk list ((20,1),(3,1);0)((20, 1), (3, 1); 0)((20,1),(3,1);0) takes 18, nine of them for feature 20 alone.

Why is this prefix-free? Read any codeword from the left, the way a decoder would. Each flag bit says whether a test follows, each feature code announces its own length, and after the end flag exactly one bit remains. So the decoder knows where the codeword ends from the symbols alone. If one codeword were a prefix of another, longer one, decoding the longer one would reach that point and stop, so the longer one could have nothing after it, which is a contradiction.

Now give each codeword the weight 1 over 2 to the power of its length: “everything is junk”, 2 bits, gets 1/4; the 7-bit list gets 1/128. Can a prefix-free code overspend, so that these weights add to more than 1? Try the small prefix-free set 0, 10, 110, 111: 1/2+1/4+1/8+1/8=11/2 + 1/4 + 1/8 + 1/8 = 11/2+1/4+1/8+1/8=1, exactly the whole budget. Shorten any word and you create a prefix. That is the general rule. (In this lemma SSS names a set of strings, not a training sequence.)

Lemma (Kraft inequality). If S⊆{0,1}∗S \subseteq \{0, 1\}^*S⊆{0,1}∗ is a prefix-free set of strings, then

∑σ∈S12∣σ∣≤1.\sum_{\sigma \in S} \frac{1}{2^{|\sigma|}} \le 1.σ∈S∑​2∣σ∣1​≤1.

Read it from the inside out: ∣σ∣|\sigma|∣σ∣ is the length of the string σ\sigmaσ, 1/2∣σ∣1/2^{|\sigma|}1/2∣σ∣ halves once per symbol, and ∑σ∈S\sum_{\sigma \in S}∑σ∈S​ adds that weight over every string in the set. In plain words: in a prefix-free code, the weights 1/2 per symbol, multiplied along each codeword, add up to at most 1. Drop prefix-freeness and it fails: 0, 01, 1 has 0 as a prefix of 01, and its sum is 1/2+1/4+1/2=1.251/2 + 1/4 + 1/2 = 1.251/2+1/4+1/2=1.25.

Proof. Start with a finite SSS, and let LLL be the length of its longest string. Toss a fair coin LLL times, with faces 0 and 1. For each σ∈S\sigma \in Sσ∈S, let EσE_\sigmaEσ​ be the event “the first ∣σ∣|\sigma|∣σ∣ tosses spell out σ\sigmaσ”. The tosses are independent and each matches its symbol with probability 1/2, so P[Eσ]=2−∣σ∣\mathbb P[E_\sigma] = 2^{-|\sigma|}P[Eσ​]=2−∣σ∣.

Now the key step. For two distinct σ,σ′∈S\sigma, \sigma' \in Sσ,σ′∈S, the events EσE_\sigmaEσ​ and Eσ′E_{\sigma'}Eσ′​ cannot both happen: if they did, both strings would be beginnings of the same toss sequence, so the shorter one would be a prefix of the longer one (or they would be equal), which prefix-freeness forbids. So the events are pairwise disjoint, and the probability of their union is the sum of their probabilities. A probability is at most 1:

∑σ∈S2−∣σ∣=P[⋃σ∈SEσ]≤1.\sum_{\sigma \in S} 2^{-|\sigma|} = \mathbb P\Big[\bigcup_{\sigma \in S} E_\sigma\Big] \le 1.σ∈S∑​2−∣σ∣=P[σ∈S⋃​Eσ​]≤1.

This is the lemma’s sum, written with a negative exponent, equal to the chance that some codeword is spelled out by the tosses. For 0, 10, 110, 111, the toss sequences starting 0, 10, 110 and 111 cover every outcome exactly once, so the chance is 1.

There is a picture worth keeping here. Read the tosses as the binary digits of a number between 0 and 1, so that 10 followed by anything is a number from 0.5 up to 0.75. The sequences that start with σ\sigmaσ then fill a stretch of that line of width 2−∣σ∣2^{-|\sigma|}2−∣σ∣: 0 owns the first half, 10 the stretch from 0.5 to 0.75. Prefix-free codewords own stretches that never overlap, and stretches that never overlap inside a line of length 1 add up to at most 1.

For an infinite SSS, every finite subset is prefix-free too, so every partial sum of the series is at most 1, and so is the series. ■\blacksquare■

Occam’s razor, and its catch

Read the MDL bound as a philosophical statement. Two hypotheses with the same empirical risk get different guarantees, and the shorter one gets the better one. In words:

A short explanation (that is, a hypothesis with a short description) tends to be more valid than a long explanation.

That is Occam’s razor, after William of Ockham, a fourteenth-century English logician who is believed to have been the first to state it explicitly. The MDL bound is one justification of it, made precise: the longer a hypothesis’s description, the more examples it must fit before its small empirical risk certifies a small true risk.

Now a puzzle, and it’s a good one. Description length depends on the language. Suppose h′h'h′ is much shorter than hhh in our list code, and both have the same empirical risk; MDL says to prefer h′h'h′. But we could have chosen a different prefix-free language, one that writes hhh in 3 bits and h′h'h′ in 100,000. Under that language, MDL prefers hhh. They are the same two lists. Which is it?

The answer is that no hypothesis is more trustworthy than another in itself. What matters is the order of events: the language must be chosen before the training sequence is seen. Recall the simplest case. If you commit to one hypothesis before seeing any data, Hoeffding gives you LD(h)≤LS(h)+log⁡(2/δ)/(2m)L_{\mathcal D}(h) \le L_S(h) + \sqrt{\log(2/\delta)/(2m)}LD​(h)≤LS​(h)+log(2/δ)/(2m)​, whatever that hypothesis is, however strange. Choosing a description language, or any weighting of hypotheses, is a weaker form of committing in advance. Instead of putting the whole commitment on one hypothesis, you spread it over many. As long as you spread it independently of the training sequence, the guarantee holds. And just as the single hypothesis could be anything, so can the language.

What breaks the guarantee is choosing the language after looking at the labels, giving the list that happens to fit a 3-bit code. Then the weights depend on SSS, the bad events in the union bound are no longer the ones you budgeted for, and the proof says nothing. Your teammate cannot pick her weights after the run.

MDL as code

Here are the two learners in pseudocode, as the theory states them: SRM from lesson 7a, beside MDL.

SRM(S, δ):
  prior knowledge: H = H_1 ∪ H_2 ∪ ..., each with gap ε_n
                   weights w(1), w(2), ... with Σ w(n) ≤ 1
  return h in argmin over h ∈ H of
         L_S(h) + ε_{n(h)}(m, w(n(h)) · δ)

What people get wrong

“Shorter descriptions are truer.” Description length is relative to a language. The razor is about committing before you look, not about any intrinsic simplicity.

“Pick the language that makes the winner short.” A language, like a weight function, encodes prior knowledge, and it must be fixed before the training sequence is seen. A language tuned after looking at the labels voids the union bound, exactly like the language puzzle in “Occam’s razor, and its catch”. The help desk’s certificate is honest because the list code was written down before its labels existed, and it would have priced any other list just as fairly.

“MDL is always better than SRM.” On the help desk it is. On the main inbox at 1,000 labels, SRM with the signed weights certifies fff at 0.1938, while MDL’s best certificate is 0.2227, for the three-test list: fff’s 29 bits cost more than its share of size 5. Weights by size and weights by bits are two different priors, and each wins on the streams it fits.

Weaker still: consistency

There is an even weaker way to define learning: let the sample size depend on the distribution as well.

A word of warning first, because of a name clash. In lesson 1, a hypothesis was consistent when it agreed with every example. Here, consistency is a property of a learning rule, borrowed from statistics, and it has nothing to do with fitting the examples. Same word, different idea.

In words first: a consistent learning rule, given enough labels, gets within ε\varepsilonε of any hypothesis you name, but “enough” may depend on the mail stream itself, so on a stream it has never met you cannot say in advance how many. The memorizer on a stream dominated by a few repeated messages needs a hundred labels; on a stream of a million equally likely messages it needs millions.

No-Free-Lunch, revisited. Lesson 5 proved that no learner learns the class of all classifiers over an infinite domain. Memorize is consistent for exactly that class. Why is that not a contradiction? Look at the order of the quantifiers. No-Free-Lunch says: for every learner and every training sequence size mmm, there exist a distribution and a labelling function on which the learner, given mmm examples, is likely to fail. Consistency of Memorize says: for every distribution and labelling function, there exists a size mmm, depending on both, beyond which Memorize is likely to succeed. No-Free-Lunch fixes mmm first and then picks a bad world; consistency fixes the world first and then picks mmm.

Which notion of learnability do you want?

We now have three definitions: PAC (one sample size for every hypothesis and every distribution), nonuniform (the size may depend on the hypothesis), and consistency (it may depend on the distribution too). Which is right depends on what you want a definition for. Let’s go through the questions an engineer would ask.

What is the risk of the hypothesis I learned? PAC and nonuniform learning both bound the true risk of the returned hypothesis by its empirical risk plus a computable term. Consistency gives no such bound. (You can always estimate the risk on held-out labelled messages, a validation set, which lesson 11 covers.)

How many examples do I need to be as good as the best hypothesis in the class? PAC gives a crisp answer before you start. Nonuniform learning does not: the number depends on the best hypothesis, which you don’t know. Consistency does not either, and the number depends on D\mathcal DD as well. In this sense PAC is the only useful definition. Keep in mind, though, that even PAC only promises to approach the best in the class: if the class has a large approximation error, the risk may still be large. And when a learner fails, PAC lets you bound the estimation error and so blame the approximation error and change the class; a nonuniform learner lets you change the weights; a consistent learner tells you nothing about which part failed, or how many more examples would help.

How do I learn, and how do I say what I know? PAC learning, through No-Free-Lunch, shows prior knowledge is necessary, gives a crisp way to state it (choose a class) and a generic learner for it (ERM). Nonuniform learning also gives a crisp way to state prior knowledge (weights over classes or hypotheses) and a generic learner (SRM). SRM is especially good at model selection, when you are unsure which class to use. Fit lists by ERM with cap 6 and you overfit, as lesson 7a’s 30-label table showed; cap them at 1 and you underfit; SRM over all sizes picks the size from the data, paying only a small extra in estimation error and the loss of knowing in advance how many examples you need. Consistency gives no learning paradigm and no way to state prior knowledge at all. Memorize needs none.

Should I prefer a consistent learner? It sounds desirable to be consistent for every function from X\mathcal XX to Y\mathcal YY: with enough data you would eventually match the Bayes optimal predictor (lesson 3: the best possible predictor of all, with true risk 0.1 on our stream). The argument has two problems. First, on the distributions you actually meet, the consistent learner may need more examples than you will ever have. Second, consistency is cheap to add. Over a countable domain with a finite label set, take any nonuniform learner: run it, compute its bound, and if the bound is small enough, return its hypothesis; otherwise fall back to Memorize. The result is consistent for every classifier. A property that easy to bolt on is a poor reason to choose one learner over another.

Recap and the next bug

  1. A description language is prefix-free when no description is the beginning of another. The Kraft inequality then says the weights 2−∣h∣2^{-|h|}2−∣h∣ add up to at most 1, so any prefix-free language is a weight function, fixed before the data.
  2. With those weights the SRM bound becomes the MDL bound, LS(h)+(∣h∣+log⁡(2/δ))/(2m)L_S(h) + \sqrt{(|h| + \log(2/\delta))/(2m)}LS​(h)+(∣h∣+log(2/δ))/(2m)​, and MDL ships the list that minimizes it: Occam’s razor, valid because the language is fixed before the data.
  3. SRM prices a list by its size class, MDL by its own bits. The help desk list has size 20 but only 18 bits, so at 1,500 labels its size-based gap is 0.1501 and its bit-based gap 0.085. For fff on the main inbox it is the other way round. Neither prior wins everywhere.
  4. MDL runs by enumerating codes in order of length and stopping once the gap alone reaches the best bound; the work is labels times length times the number of codewords tried.
  5. Consistency lets the sample size depend on the distribution too. Memorize is universally consistent over countable domains, which shows how weak that promise is.

Then the operations team runs the main filter on the real mail stream, where hundreds of features are in use, and the training job never finishes. Of course it doesn’t: with 1,000 labels, SRM’s stopping rule has to examine lists up to size 22, about 1.55×10281.55 \times 10^{28}1.55×1028 of them, and MDL has to reach codes of 96 bits. The statistics are fine; a thousand labels are enough. The computation is hopeless. So far we have only asked how many examples a learner needs.
